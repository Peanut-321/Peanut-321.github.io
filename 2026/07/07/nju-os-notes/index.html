0. 目标与学习范围

这条路线以 JYY OS 2022 版 handbook 和实验为主，全程使用 Mac 作为开发机，安排 8 个学习周，为嵌入式软件、BSP、SoC 方向打基础。默认已经接触过 C、指针和 RoCC 裸机程序，每周投入约 12–15 小时；L1、L2 调试超出预期时，可增加 1–2 周。课程框架的 macOS 适配需要单独验证，不承诺八周内完成全部平台移植和隐藏测试。

我的目标是：

目标 学完后要能做什么
理解 OS 解释程序运行、中断、调度、地址空间、设备访问之间的关系
用好 gcc 分清预处理、编译、汇编、链接；检查 ELF、符号、反汇编和编译选项
用好 Makefile / make 看懂真实构建命令、变量和依赖，定位构建失败与漏编译
用好 gdb / LLDB 在 Mac 调试本机程序，在 QEMU 调试实验内核，观察断点、调用栈、内存和寄存器
理解 Unix / Linux 在 macOS 实践通用进程、FD、管道、权限，识别 Linux 专属接口，后续在 RoCC 的 QEMU Linux 环境补验证
为驱动与面试准备 给已有的 RoCC 后续开发提供 OS 基础，用实验现象解释八股问题

实践只使用 JYY 的实验。真实驱动开发沿用已有的 RoCC 裸机 HAL → QEMU 设备模型与 Linux 驱动 M0–M3 计划，不在这条路线里重复安排项目。OS 阶段的终点，是能够读懂后续驱动方案并说明它为什么这样设计；写出完整驱动属于后续项目的交付。

学习顺序：

  • 2022 课程目录与讲义
  • 2022 实验须知：环境、框架与 Makefile 导读
  • 课程概述：应用视角与硬件视角
  • AbstractMachine：裸机运行环境与 API

下面的优先级是针对我的岗位目标制定的，不是课程官方要求。

实验 本轮安排 主要收益
M1 pstree 做精简 macOS 适配版 进程枚举、父子关系、命令行、错误处理；原版 /proc 部分读懂
L0 amgame 必做，游戏保持简单 裸机 C、AM、运行库、编译与链接

L1 pmm 必做 分配器、对齐、碎片、多处理器安全
L2 kmt 重点必做，分配最多时间 中断、内核线程、自旋锁、信号量、调度
M3 sperf 本轮读懂，运行后置 依赖 Linux strace，留到已有 QEMU Linux 开发阶段补
M4 crepl 做 macOS 适配版 fork/exec、编译器调用、Mach-O 动态库、dlopen/dlsym
L3 uproc 学原理，完整实现后置 用户态、页表、系统调用、进程隔离

M5 frecov 存储方向再做 FAT32 镜像与文件恢复

L4 的名称来自官方课程目录；本次访问其独立手册页未成功，暂以目录中的讲义为入口，不据此补写未核对的实现要求。

本轮主线是 M1 适配版、L0、L1、L2、M4 适配版。 M2 移植选做，M3 留到 Linux 客体环境；L3、L4 的实现、M5、完整 xv6 源码和 Android 专题后补。虚拟内存、系统调用和设备的基础概念仍需掌握。macOS 适配版只代表保留学习目标，不代表满足原版 Linux OJ 要求。

2. 环境：Mac 开发，QEMU 运行实验内核

macOS 有 Unix/POSIX 基础，适合练 C、Shell、文件、进程和线程。它使用的内核、进程查询接口、可执行文件格式和调试接口，与 Linux 存在差异。Unix 身份不意味着 Linux 程序可以原封不动运行。参见 Apple BSD 概述 和 UNIX 产品登记。

本路线采用两种运行方式，编辑、构建与调试操作都在 Mac 上：

内容 运行位置 需要处理的差异
通用 C、Unix API、M1/M4 适配版 macOS 本机进程 /proc、Mach-O、动态库和调试工具
L0/L1/L2 教学内核 Mac 上的 QEMU 交叉编译、ELF 链接、课程脚本兼容性
后续 Linux 驱动 现有 RoCC 计划中的 QEMU Linux 客体 Linux 内核与驱动接口，在项目阶段处理

OS Lab 的 QEMU 里运行自己写的裸机程序或教学内核，不要求另装一套 Linux 桌面、使用远程 Linux 主机。若完全不使用模拟器，只运行 macOS 本机进程，L0/L1/L2 就不能按裸机实验原样开展。

本机已核对的工具

2026-10-20 检查结果：Apple Silicon/arm64、macOS 15.7.4；/usr/bin/gcc 实际是 Apple Clang 17；系统 make 是 GNU Make 3.81；LLDB 可用；常见 Homebrew bin 路径未发现 GNU GCC、GDB 或 QEMU。本次只检查环境和修订路线，没有安装软件，也没有跑通 JYY 实验框架。

工具按目标区分：

  • 本机编译： Clang 可先练编译流程；学习 GNU GCC 时使用 Homebrew 的 GNU GCC，并在 Makefile 中显式指定实际的 gcc-版本号。安装后用 --version 确认，不根据命令名猜。
  • 本机调试： LLDB 直接用于 macOS 程序；同时学习对应的 GDB 命令，核心调试方法相通。
  • 实验内核： 使用能生成选定 QEMU 目标 ELF 的交叉编译工具链；普通 Darwin 目标 GCC 不等于裸机交叉编译器。
  • GDB 训练： 用支持该客体架构的 GDB 连接 QEMU gdbstub；先验证 ELF 加载、架构识别和断点。Mac 本机附加调试则另外核对目标支持与签名权限。
  • 构建工具： 课程若用到新版本 GNU make 特性，可安装并显式调用 gmake；脚本中的 GNU/BSD 工具差异按实际报错处理。

来源：Homebrew GNU GCC、GDB、QEMU、QEMU GDB 调试文档。这些资料证明工具可获取及调试方式，不等于 2022 课程框架已在本机验证通过。

课程框架适配原则

获取 2022 框架后先锁定版本。原版 Mini Lab Makefile 明确使用 -m32/-m64 和共享库规则；Apple Silicon 原生 arm64 构建不能照抄。

保留官方文件作为参照，为 Mac 单独维护构建入口和必要的平台适配；不为追求“能编译”关闭关键警告。本机先验收 arm64，不声称完成官方 x86 32/64 位测试。

L0 开始前先完成一个环境检查：所选 2022 AM 版本支持的目标架构、交叉工具链、链接器/objcopy 与 QEMU 匹配，最小 AM 程序能启动。优先沿用该版本已提供的 QEMU 目标，不另写整套 AM 的 ARM64 移植。这个适配尚未完成；不能把当前 AM 主分支的能力直接当成 2022 版能力。

自学验收使用本地回归、断言和调试记录。官方 OJ 面向本校开放，不把获得 OJ 权限作为开始学习的前提。

3. 八周安排

“学习周”按实际投入计算；实习、课程繁忙时可以分散到多个日历周。已有 RoCC 计划中的 RTL、HAL 和 QEMU 驱动工作保持原安排。

学习周 课程主题 实验与工具 本周验收
第 1 周 OS 概述、Unix 进程、工具链 M1 macOS 适配版；Clang/GCC、make、LLDB 构建进程树，定位一个真实错误，解释与 /proc 方案的差异
第 2 周 AM、裸机、状态机模型 L0；交叉编译、QEMU、GDB 先通过环境检查，再跑简单游戏，解释裸机构建路径
第 3 周 并发、互斥、同步 课程示例、L1 起步；M2 读机制 解释共享状态与数据竞争，分配器单执行流路径正确
第 4 周 物理内存与共享状态 L1；断言、随机测试 分配/释放正确、满足规约对齐、多执行流下不分配重叠区域
第 5–6 周 中断、上下文、调度 L2；锁、信号量、线程状态 线程可运行、阻塞、唤醒，解释一次完整切换
第 7 周 Unix 进程、编译与动态加载 M4 macOS 适配版；fork/exec、dlopen 调用编译器、加载函数、计算表达式并处理失败
第 8 周 地址空间、设备、Linux 差异 重点讲义、M3 原理、面试复盘 讲清地址、阻塞唤醒、缓冲区寿命及尚未验证的 Linux 行为

每周大致分配：3 小时讲义/视频、7–9 小时编码与调试、2–3 小时复盘和面试问答。优先读讲义与运行示例，视频按卡点补看。

L2 没有完成时，用缓冲周继续修，不为了按期打勾直接跳到驱动。若目标只是先进入 RoCC 裸机 HAL 开发，第 2 周的工具链与裸机基础已经可以开始发挥作用。

4. 第 1 周：M1 适配版、Unix 与工具链

阅读“操作系统概述”“操作系统上的程序”以及 M1 pstree。保留打印进程父子树的目标，平台信息获取层改成 macOS API；不额外扩大项目。

Unix 的学习范围

围绕实验使用目录、文件、返回值与 errno、stdin/stdout/stderr、管道、重定向、PATH、权限、PID/PPID。Shell、fork/exec、pipe、pthread 等大量知识能迁移到 Linux；/proc、epoll、Linux 内核模块等需要另外识别。

要解决的问题 Mac 上使用的工具或接口
查 API 和返回值 man 2、man 3、系统 SDK 头文件
查看进程与父子关系 ps；实现时核对 libproc 的 proc_listpids/proc_pidinfo
找文件和代码 find、rg
过滤、比较输出 grep、sort、diff、less
看权限和环境 ls -l、env、echo “$PATH”
定位变量、栈和内存错误 LLDB

macOS 没有 Linux 的 /proc 进程目录。已在本机 SDK 的 libproc.h 和 sys/proc_info.h 确认相关声明；实际返回值、可见范围和权限仍按 API 检查。枚举期间进程可能退出，需要处理查询失败。

验收： 保留一次“现象 → 假设 → 断点/观察 → 根因 → 修复 → 回归”的记录，并明确进程枚举使用的是 macOS API。

面试对应： 程序与进程、PID/PPID、库函数与系统调用、编译与链接、Unix 通用接口与平台扩展。

5. 第 2 周：L0、裸机和 Makefile

阅读 AbstractMachine 及 L0 amgame。先按环境检查跑通最小裸机程序，再写足够验证输入、输出和主循环的简单游戏。Mac 负责构建，QEMU 负责执行客体指令；Mac 的 ARM64 CPU 不要求教学内核也使用 ARM64。

AM 接口分阶段学习：

API 现在需要理解的作用
TRM 最小 C 执行环境、输出、停机
IOE 设备输入输出
CTE 中断、异常、上下文；L2 时深入
MPE 多处理器、原子操作；L1/L2 时深入
VME 地址空间与映射；第 8 周深入

沿着实际 Makefile 的 include 关系，找到交叉编译器、编译选项、ELF 链接过程与启动入口；使用匹配客体架构的 nm/readelf/objdump 检查输出，区分 section 与 segment。不要用 Apple 的 Darwin 链接器直接替代课程的 ELF 链接器。

Makefile 必须能解释的内容

  • target、prerequisite、recipe，以及文件时间戳如何决定重建。
  • =、:=、?=、+=，命令行变量覆盖。
  • $@、$<、$^、模式规则、include、.PHONY。
  • CC、CPPFLAGS、CFLAGS、LDFLAGS、LDLIBS 的职责。
  • -MMD -MP 与 .d 文件如何追踪头文件依赖。
  • 并行构建为什么依赖正确的依赖图。

参考 GNU make 手册 与 GCC 依赖生成选项。在笔记里重写当前实验的一条编译规则和一条链接规则，并逐项解释；暂不研究构建系统的复杂技巧。

QEMU 启动参数中加入 gdbstub 配置后，可由匹配客体架构的 GDB 加载对应 ELF，执行 target remote localhost:1234；端口以实际启动配置为准。练断点、单步、寄存器和内存观察，参见 QEMU GDB 文档。

验收： 裸机程序可启动且调试器能命中断点；修改源文件或头文件后能预测并验证重建；能从日志说明工具链失败在哪一步。

RoCC 对应： 理解裸机 benchmark 的入口、运行库、链接脚本、交叉编译器，以及 riscv64-unknown-elf-* 与 Linux 目标工具链服务于不同运行环境。AM 的 x86 切换实现不需要照搬到 RISC-V。

面试对应： main 之前发生什么、.data/.bss、栈和堆、静态/动态链接、交叉编译与 ABI。

6. 第 3 周：并发原理，M2 移植选做

先学“多处理器编程”“理解并发程序执行”“互斥”“同步”“并发 Bug”。可在 macOS 用课程中可移植的 pthread/C 示例观察共享状态与同步，再开始 L1。

阅读 M2 libco，理解独立栈、协作式 yield、等待与回收。它是用户态协程库，共享一个内核线程时不会自动获得多核并行。

2022 手册的构建与汇编示例面向 x86。移植到 Apple Silicon 要核对 AArch64 调用约定、需要保存的寄存器、栈对齐和 macOS 汇编/链接差异；仅替换编译命令不足以完成。M2 移植本轮选做，L2 会继续实际训练上下文与切换，不把精力耗在额外平台移植上。

验收： 能解释数据竞争、互斥与同步，画出协程独立栈和 yield 前后的执行位置；L1 的基本数据结构开始可测试。

面试对应： 进程/线程/协程、并发与并行、协作与抢占、原子性、死锁条件。

RoCC 对应： 软件暂时不运行时，加速器仍可能运行；共享硬件状态需要明确所有权。

7. 第 3–4 周：L1 与内存管理

做 L1 pmm。沿用 L0 已验证的 Mac 交叉编译与 QEMU 环境；不把原版 ARCH=native 直接视为 macOS 兼容目标。实验要求多处理器安全，不能把单执行流下分配成功当成完成。

先实现清楚、可验证的分配与回收，再检查并发与性能。重点掌握空闲块、元数据、分裂/合并、内部/外部碎片和溢出边界。按手册的对齐规约实现，例如申请 17 字节需满足 32 字节对齐；不要用主机 malloc 的习惯替代实验规约。

本地检查至少包含：

  • 多次申请返回的存活区域互不重叠。
  • 块大小、对齐和堆边界正确。
  • 分配后写入标记，其他分配不破坏标记。
  • 释放后可以重新利用，耗尽时正确失败。
  • 多执行流反复分配/释放仍保持不变量。

用断言检查边界与链表状态，记录随机测试种子。自写检查用于定位问题，不把“简单压力测试通过”表述成已满足所有 hard test 的性能要求。

验收： 能解释分配器的元数据、临界区和正确性不变量，能定位一次越界或重叠分配问题。

面试对应： 内存池、碎片、对齐、malloc/free、越界、use-after-free、内存泄漏。

RoCC 对应： 缓冲区对齐、长度和生命周期。L1 负责物理堆中的分配；Linux 用户态 malloc 返回的是虚拟地址，不能直接据此推断设备能访问的地址。

8. 第 5–6 周：L2 是核心

阅读中断、上下文切换、调度相关内容，做 L2 kmt。L2 在 L1 上加入中断处理、内核线程、自旋锁和信号量，优先保证 L1 的基础正确性。

建议按以下顺序推进：

  1. 看懂 CTE 的事件与 Context，跟踪进入处理函数和返回的路径。
  2. 创建一个线程，检查初始栈与第一次运行。
  3. 跑多个线程，检查上下文保存、恢复与状态转换。
  4. 按实验要求处理多处理器共享状态和锁。
  5. 实现信号量的阻塞、唤醒与生产者/消费者场景。
  6. 检查中断嵌套、退出临界区和资源回收。

必须回答：

  • 中断入口保存现场、普通函数调用、线程切换分别做了什么？
  • 为什么关本地中断不能解决多核互斥？
  • 线程持有锁时被同核中断打断，而处理函数又要同一把锁，会发生什么？
  • 阻塞线程为什么不会继续占用 CPU？
  • 等待条件的检查与加入等待队列之间，怎样避免丢失唤醒？

mutex 适合允许睡眠的线程/进程上下文；普通硬中断上下文不能获取会睡眠的 mutex。自旋锁用于短临界区，但也有上下文和内核配置约束。Linux 的具体 API 用法在后续驱动阶段按目标内核核对，不能把教学内核的实现直接搬过去。

验收： 画出“运行 → 阻塞 → 就绪 → 再运行”，并用日志解释一次真实调度；多线程生产者/消费者能运行，不靠延时凑同步。

面试对应： 上下文切换、调度、临界区、mutex/spinlock/semaphore、忙等与睡眠、优先级反转。

RoCC 对应： 给全局单实例加速器设计所有权；锁要覆盖完整的配置与运行事务，不能只保护某一次写地址。后续 completion/等待队列为什么能让进程睡眠，也从这里理解。

9. 第 7 周：M4 适配版与 Unix 系统编程

阅读“操作系统上的进程”“系统调用和 UNIX Shell”“C 标准库的实现”“可执行文件与加载”，完成 M4 crepl 的 macOS 适配版。

M4 的学习目标是逐行接收函数或表达式，调用编译器生成代码，动态加载后在主进程求值。macOS 提供 fork/exec、dlopen/dlsym，但原版 ELF .so 构建要改为 Darwin/Mach-O 动态库的正确选项和符号解析规则，不能只把后缀改成 .dylib。

围绕该实验掌握：

  • fork、execve、waitpid、环境变量与编译器路径。
  • 调用真正的 GNU GCC 与调用 Apple Clang 的差异。
  • 临时文件、编译失败、错误输出与资源清理。
  • 动态库加载、函数指针、符号可见性、重复输入。
  • 父子进程继承的 FD、重定向及 EOF；使用管道时正确关闭端点。

遵循手册禁止 system/popen 的约束，练习实际进程 API。用 LLDB 调试本机主进程；不照搬 Linux strace 或 GDB 的所有 fork 调试设置。

验收： 能定义并调用函数、计算表达式；非法输入或编译失败不会导致主程序随意崩溃；能解释编译器子进程与主进程动态加载之间的关系。

M3 放在哪里

M3 sperf 依赖 Linux strace。macOS 上的 dtruss/DTrace 有权限与系统限制，输出格式也不同，不作为本轮可直接替换的前提，更不为做实验去关闭系统保护。

本轮读懂 fork/execve/pipe、捕获 trace、解析统计的设计；以后在已有 RoCC QEMU Linux 客体中补跑原版 M3。其 Linux 运行结果、/proc、Linux 系统调用名称与驱动行为，不能仅凭 Mac 适配版就宣称已掌握。

面试对应： fork/exec/wait、僵尸进程、管道与 FD、编译/链接/加载、动态库与函数指针。

10. 第 8 周：地址空间、设备与面试串联

这一周以讲义和代码走读为主，不要求新增完整 Lab。

地址空间：为 RoCC 的内存问题做准备

重点读“进程的地址空间”“可执行文件”“可执行文件的加载”，结合 L3 手册理解：

  • 虚拟地址、物理地址、页表、TLB、缺页。
  • 用户态/内核态、访问权限、系统调用边界。
  • ELF 如何映射进地址空间，栈和堆如何出现。
  • 两个进程中数值相同的指针为什么可能访问不同内存。
  • 线程/进程切换后，异步硬件访问原地址需要什么保证。

验收： 能区分 CPU VA、CPU PA、设备 DMA 地址；能解释“指针强转成整数”不会替硬件完成地址翻译。

设备与文件：读懂驱动所在的位置

阅读“输入输出设备”“设备驱动程序”“文件系统 API”，再概览 FAT/UNIX 文件系统与持久性：

  • 轮询与中断各有什么成本。
  • open/read/write/ioctl 如何进入驱动接口。
  • 字符设备、块设备、VFS 分别提供什么抽象。
  • 设备忙时如何等待，完成后如何通知。
  • close、超时、进程退出与硬件停止是什么关系。
  • 写入返回、缓存更新、持久化和掉电一致性为什么不是同一个保证。

macOS 原生用户态练习不能验证 Linux platform/设备树/DMA API，也不能把 Linux 内核模块加载进 macOS。后续在 Mac 上运行已有 RoCC 计划中的 QEMU Linux 客体来学习与实现；Mac 仍是开发机。Linux 的地址模型参考 DMA API HOWTO。

验收： 能画出“应用 → 系统调用 → 文件操作 → 驱动 → 硬件”，并用 RoCC 任务的提交、等待和完成说明每层职责。

11. 与已有 RoCC 后续开发衔接

RoCC 后续开发沿用现有修订方案：裸机 HAL、QEMU 设备模型与 Linux 驱动 M0–M3；本路线补齐它们需要的 OS 基础。

后续工作 现在重点学习的内容 进入该工作前应能回答
裸机 HAL：分层、参数检查、超时轮询 L0、gcc、Makefile、ABI 指令封装、驱动层、应用层各自负责什么？
M0：platform/MMIO、同步 RUN、复制与 coherent buffer M1/M4 的 Unix 基础、地址空间、设备讲义 ioctl 为什么要复制用户数据？设备地址从哪里来？
M1：中断、completion、睡眠等待 L2、中断、阻塞/唤醒 完成早于等待时怎样不丢事件？
M2：mmap、多进程、单任务所有权 L1/L2、进程隔离与生命周期 两个进程怎样不覆盖全局地址？close 后映射一定消失吗？
M3：watchdog、漏中断、超时离线 并发状态机与资源回收 超时返回以后，硬件是否还可能写缓冲区？

这里的 M0–M3 是 RoCC 驱动里程碑，与 JYY 的 Mini Lab 编号是两套命名。

需要始终保留的边界：

  1. 现有项目采用 RoCC 自定义指令控制，访存走 HellaCache；后续 QEMU 模型模拟拟议的 MMIO/DMA 外设。两者的验证结论不能直接互换。
  2. 按既有方案记录的现有请求 phys=false，地址走 CPU 翻译上下文；只加 MMIO 和中断，不会自动变成可直接接收 dma_addr_t 的独立 DMA 主控。
  3. 缓存一致性、物理连续性、地址空间有效性分别分析。fence 处理顺序问题，不能代替地址翻译、缓冲区寿命管理或所有平台的缓存同步。
  4. QEMU 适合验证驱动协议、并发和故障路径；真实缓存关系、RTL 周期和总线背压仍要依赖对应硬件/RTL 证据。

RoCC 接口关系参考 Chipyard 官方文档，设备地址与缓存管理参考 Linux DMA 文档。具体实现以项目锁定版本为准。

12. 面试八股：每题绑定证据

每周学完就练口述，不等八周结束后再集中背。每题按“概念 → 机制 → 实验或项目例子 → 边界条件”组织，先练 1–2 分钟，再接受追问。

主题 需要讲清的问题 可用证据
程序运行 编译/链接/加载分别做什么？main 前有什么？ M1/M4 适配版、L0 启动路径
存储布局 .data/.bss、栈/堆、对齐有什么区别？ ELF、反汇编、L1
进程线程协程 各自共享和独立什么？谁负责切换？ M2 原理、L2、M4 适配版
用户态与内核态 系统调用如何进入内核？libc 是否就是 syscall？ 讲义、M4 进程操作；M3 trace 后补
并发同步 数据竞争、原子性、死锁、丢失唤醒 并发示例、L1/L2
锁与中断 mutex 与 spinlock 怎样选？关中断保护了什么？ L2、RoCC 所有权设计
内存管理 碎片、越界、UAF、页表、TLB、缺页 L1 与地址空间讲义
Unix IPC fork/exec/wait、pipe、FD、EOF；Linux 有哪些差异？ M4 适配版与讲义；M3 后补
设备访问 轮询/中断、阻塞唤醒、ioctl、mmap 设备讲义、后续 RoCC
硬件内存 CPU VA/PA/DMA 地址、缓存一致性、屏障 地址空间、RoCC 方案
错误处理 等待超时后能否立即释放 buffer？ L2 生命周期、后续 watchdog
C 与优化 volatile 能否保证原子性和同步？优化为什么影响调试？ 并发讲义、gcc/反汇编

volatile 不能代替锁、原子操作与内存屏障；Linux 驱动通常使用相应内核同步原语与设备访问 API。参考 Linux 对 volatile 的说明。

其中优先练 RoCC 方案里的六条主线：RoCC/MMIO、三种地址、全局单实例所有权、mutex/spinlock、中断状态与清除、超时与硬件停止的区别。OS 实验提供原理证据，后续项目补实现证据。

13. 记录方式与停止条件

每个实验只保留一份简明记录：

一个实验的本轮收口标准是：核心 API 按规约实现，自己设计的正常/边界/失败场景有回归，能解释关键机制和已知不足。性能和复杂并发仍有问题时如实记录，不把“能跑”写成“完全正确”。

进入 RoCC Linux 驱动阶段前，重点自查：

  • 能区分 Apple Clang、GNU GCC 和裸机交叉编译器，用 make 日志定位构建问题；本机用 LLDB，QEMU 客体用匹配目标的 GDB。
  • 能解释一次中断、线程切换、阻塞和唤醒。
  • 能区分 VA/PA/DMA 地址，并说明缓冲区何时可以回收。
  • 能说明单实例硬件的并发边界与完整锁范围。
  • 能解释等待超时不等于硬件停止。

满足这些条件就进入已有项目。M2 移植、M3、L3、L4 和 M5 按实际卡点继续补；Mac 上已验证的通用能力与尚未运行的 Linux 专属内容分别记录，不把“先学完整门课”设为驱动开发的无限前置条件。
