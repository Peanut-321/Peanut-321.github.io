0. 项目概览

SRCNN（Super-Resolution Convolutional Neural Network）是一个结构简单但计算密集的三层超分辨率网络。这个项目的目标不是重新训练网络，而是把已经确定的 SRCNN 推理过程映射到 FPGA：在 PS（Processing System）端完成图像准备、内存管理和加速器控制，在 PL（Programmable Logic）端完成高吞吐的三层卷积计算。

  • Repository：SRCNN-HLS-Accelerator
  • Target board：AMD Kria KV260 / K26 SOM
  • HLS toolchain：Vitis HLS + Vivado
  • Host runtime：PYNQ / Python
  • 当前阶段：Golden Reference 和 host 端定点验证已完成；HLS 综合、PL/PS 集成与板上性能测试仍在推进

1. 为什么选择 SRCNN 做 FPGA 加速

SRCNN 只有三层，但一次 255×255 推理包含超过 5 亿次 MAC。卷积的循环边界固定、访存规律明确，同一个权重会在整幅图像上重复使用，相邻窗口也会重复读取大量像素。这些特征很适合通过 FPGA 的并行乘加、片上缓存和流式流水线进行加速。

CPU 上的朴素实现会反复执行索引计算、边界判断、load/store 和串行累加。FPGA 侧则可以把这些工作变成固定的数据通路：line buffer 保留相邻行，window buffer 每拍移动窗口，多组 DSP 并行完成 MAC，层与层之间通过 FIFO 直接传递 feature map。

真正的挑战并不只是“多放几个乘法器”，而是同时处理以下问题：

  • Conv1、Conv2、Conv3 的计算密度差异很大，需要合理分配 DSP；
  • 中间 feature map 很大，不能直接全部放进片上 BRAM；
  • 展开 MAC 后，权重和窗口存储必须提供足够的并行读端口；
  • 定点化必须在资源、吞吐和图像质量之间取得平衡；
  • PS/PL 之间的 DMA、cache coherence、TLAST 和超时处理必须可靠；
  • 性能必须区分 kernel-only、DMA 和端到端耗时。

2. 网络结构与功能契约

本项目采用经典的三层 SRCNN。输入是已经完成 bicubic 放大的单通道 255×255 tensor，三层均使用 stride 1，并通过 replicate-edge padding 保持空间尺寸不变。

逻辑卷积采用 cross-correlation，即不翻转 kernel：

$$
Y[o,h,w] = b_o + \sum_c \sum_i \sum_j
W[o,c,i,j]X[c,\operatorname{clamp}(h+i-P_h),\operatorname{clamp}(w+j-P_w)]
$$

计算顺序固定为 accumulator = bias，随后执行 MAC；Conv1 和 Conv2 在完整累加后做 ReLU，Conv3 不做 ReLU、round 或 clamp。激活使用 CHW 布局，权重使用 OIHW 布局，bias 使用 O 布局。

层 Kernel 输入/输出通道 Padding 半径 激活 每个输出位置的 MAC
Conv1 9×9 1 → 64 4 ReLU 81/输出通道，合计 5,184
Conv2 1×1 64 → 32 0 ReLU 64/输出通道，合计 2,048
Conv3 5×5 32 → 1 2 无 800

这里最容易出错的是边界语义。课程部署路径要求 replicate-edge，而早期内部回归还保留 zero-same 和 valid 两种模式。它们只用于检查索引，不应被误当作最终部署行为。

3. 系统架构：PS 与 PL 如何分工

K26 是 Zynq UltraScale+ MPSoC，既包含 ARM 处理器，也包含 FPGA 可编程逻辑。本项目计划按以下方式划分系统：

PS 端职责

  • 读取输入图像和模型参数；
  • 完成颜色空间转换、bicubic resize、归一化和最终显示等非核心操作；
  • 加载 .bit/.hwh overlay；
  • 使用 PYNQ 分配物理连续 buffer，并按硬件数据格式打包；
  • 配置控制寄存器，启动 MM2S/S2MM DMA；
  • 处理 cache flush/invalidate、超时与错误恢复；
  • 将硬件输出与 Golden Reference 比较，并记录端到端时间。

PL 端职责

  • 接收已经预处理好的单通道 tensor；
  • 使用定点数完成 Conv1、Conv2、Conv3；
  • 在边界处实现 replicate-edge；
  • 使用 line buffer/window buffer 复用空间数据；
  • 通过 pipeline、unroll、array partition 和 dataflow 提高吞吐；
  • 尽量让三层 feature map 在 PL 内以 stream 形式传递，避免写回 DDR；
  • 输出单通道 SRCNN 结果，并正确产生 AXI stream sideband 信号。

这一划分让 PL 专注于规则、重复、计算密集的卷积，PS 则保留文件系统、图像处理、内存管理和实验控制等灵活工作。

4. 工作量分析：优化应该花在哪里

对于一帧 255×255 输入，三层都输出同样的空间尺寸。静态计算量如下：

层 输出元素 MAC/输出 MAC/帧 占总 MAC
Conv1 4,161,600 81 337,089,600 64.54%
Conv2 2,080,800 64 133,171,200 25.50%
Conv3 65,025 800 52,020,000 9.96%
Total 6,307,425 — 522,280,800 100%

因此 Conv1 是主要计算热点，Conv3 虽然总计算量较小，却拥有最深的 800 项累加，对累加器位宽和数值误差最敏感。

中间特征图同样决定了系统架构。在 32-bit 数据下，Conv1 和 Conv2 的 feature map 分别约为 15.88 MiB 和 7.94 MiB，远大于适合整帧驻留 BRAM 的规模。如果两层中间结果都写回 DDR，再由下一层读回，单帧理论最低流量约 50.49 MB；如果三层融合，仅让输入、参数和最终输出跨越 DDR，理想下界约为 0.55 MB。

这也是后续优先考虑 line buffer + layer fusion + DATAFLOW 的原因：目标不仅是减少 cycle，也要避免 DDR 成为系统瓶颈。

5. Golden Reference：先把“正确”定义清楚

5.1 顺序 C++ 参考实现

在进行 HLS 优化前，我先实现了一个没有硬件优化语义的 C++17 Golden Reference。它支持三层独立运行、完整网络推理、CHW/OIHW tensor 检查、逐层 dump 和固定随机种子。

当前测试覆盖：

  • 全零、bias-only 和 all-ones 手算；
  • impulse 与 sparse weight，用于检查 kernel 方向和通道映射；
  • 正负值、ReLU 边界、中心/边缘/角落；
  • same/valid padding 对照；
  • 非方形、非 2 的幂尺寸；
  • tensor 短读、多读、layout 和 checksum 错误；
  • 完整三层随机回归。

5.2 为什么还需要独立 Python oracle

如果测试向量和被测程序都由同一套 C++ 索引生成，一个系统性 bug 可能同时存在于“答案”和“实现”中。仓库中的 tools/cross_validate_golden.py 不调用 C++ 代码，而是直接从 tensor 文件按卷积定义重新计算每一层。

验证时不仅检查最大误差，还记录最坏坐标、行列错误分布和 ReLU 的 zero flip。边界错误通常集中在首尾行列，而普通浮点累加噪声会更均匀，这些统计能帮助判断错误来源。

5.3 当前证据

  • 14/14 Golden 单元测试通过；
  • 五套固定向量通过独立 oracle；
  • -ffp-contract=off 下，当前机器上的 O0/O3 输出逐位一致；
  • 官方参考数据验证了 255×255 + replicate-edge + bias-first 功能契约。

Golden Reference 的作用不是追求速度，而是成为后续 C simulation、RTL co-simulation 和板上输出都必须对齐的数值基准。

6. 定点化：从 float32 到 ap_fixed

浮点在验证阶段直观，但在 FPGA 上通常会消耗更多资源并带来更长的数据通路。HLS 实现把拓扑、算术和结构优化分开：

  • project_config.hpp 保存网络拓扑、动态范围假设和结构参数；
  • numeric_config.hpp 推导 data_t 和各层 accumulator；
  • arithmetic.hpp 统一 MAC、ReLU、舍入与饱和语义；
  • srcnn_hls.cpp 只负责循环结构和索引。

对于一层含有 $N$ 个乘积的卷积，累加器上界不能只考虑 MAC，还要包括 bias：

$$
|acc|{max} \le N\cdot |X|{max}\cdot |W|{max}+|b|{max}
$$

当前 host 验证使用 ap_fixed<32,24,AP_RND_CONV,AP_SAT>，即 Q24.8。它是为了验证定点链路和测试机制而选择的安全占位格式，不是最终部署格式。正式位宽必须在恢复训练权重和课程图像后，根据逐层动态范围、饱和计数、PSNR/SSIM 和综合资源共同决定。

随机回归向量的阶段性结果如下。由于权重并非训练权重，且这里的 PSNR 使用 R=1，这些数字不能代表最终图像质量。

Conv1 0.0340617 0.00328683 0.00585480 0.25499%–0.27560% 0
Conv2 0.146804 0.0135622 0.0232854 0.28420%–0.35468% 0
Conv3 1.94983 0.591728 0.690314 0.27088%–0.62282% 0

当前 HLS top 为 srcnn_hls_top，自然循环顺序为：

基线版本刻意不加入 PIPELINE、UNROLL、ARRAY_PARTITION、DATAFLOW 或接口 pragma。这样第一次 csynth 可以暴露最原始的 latency、memory port conflict 和资源映射，为后续每项优化提供可比较的起点。

计划采用的优化顺序为：

  1. baseline-csynth：保存未优化 top 的 schedule、latency、II、clock 和资源报告；
  2. axi-stream-interface：固定 TDATA packing、TKEEP、TLAST 和传输长度；
  3. line-buffer：把重复的 frame 访问替换为滑动窗口；
  4. pipeline：流水化像素/窗口循环，定位依赖与存储端口限制；
  5. unroll-partition：按 DSP 预算展开 MAC，并对权重和 buffer 做匹配的 partition；
  6. dataflow：使用 stream/FIFO 连接三层，调节 FIFO 深度并排除 deadlock；
  7. board-mvp：导出 IP、生成 bitstream，并在 KV260 上完成正确性和计时；
  8. ablation-report：从最终版本逐项关闭优化，记录至少三组受控对比。

每个 checkpoint 都应保持相同的输入、权重、padding、目标时钟和测量边界。只要数值回归失败，这个版本就不能成为下一项优化的基础。

8. PL 端设计记录

本节描述目标架构。接口位宽、展开因子、FIFO 深度和实际时钟要以 Vitis/Vivado 报告为准。

8.1 AXI 接口

计划采用 AXI4-Stream 传输输入与输出，AXI4-Lite 负责启动、状态和必要配置。需要明确记录：

  • TDATA 位宽与每 beat 打包的元素数；
  • signed fixed-point 在 byte stream 中的排列和 endianness；
  • 非整 beat 尾部的 TKEEP；
  • 每帧 TLAST 的位置；
  • input/output/weight 的传输长度；
  • free-running、ap_ctrl_hs 或其他控制协议；
  • reset 极性、DMA 超时和错误恢复策略。

8.2 Conv1：9×9 空间卷积

Conv1 占总 MAC 的 64.54%，是并行化的首要目标。流式实现需要保留前 8 行输入，并从 line buffer 中形成 9×9 window。权重只有 5,184 个，原则上可以片上驻留，但具体映射到 BRAM、LUTRAM 还是寄存器阵列要由综合报告确认。

记录项：

  • line buffer 的数据类型、bank 数与实际 BRAM/LUTRAM；
  • MAC unroll factor；
  • pixel loop 的 achieved II；
  • 64 个输出通道的复用/并行策略；
  • replicate-edge 是否在窗口生成阶段完成；
  • Conv1 输出速率能否与 Conv2 消费速率匹配。

8.3 Conv2：1×1 通道混合

Conv2 不需要空间窗口，但每个输出通道需要归约 64 个输入通道。它更像逐像素的矩阵向量乘法，优化重点是 channel unroll、权重 banking 和 Conv1/Conv2 之间的 stream layout。

记录项：

  • 每拍输入通道数；
  • 32 个输出通道的并行度；
  • 权重 array partition 方式；
  • 部分和累加树的 latency；
  • 与 Conv1 stream 的通道顺序转换成本。

8.4 Conv3：5×5 重建层

Conv3 需要 4 行 × 32 通道的历史数据，理论 line-buffer payload 为 32,640 个元素。每个输出包含 800 项累加，因此需要重点关注 accumulator 位宽、DSP 复用和 partial sum 的关键路径。

记录项：

  • 多通道 line buffer 的 banking；
  • 5×5×32 MAC 的分组方式；
  • accumulator 位宽和饱和事件；
  • achieved II 与 timing slack；
  • Conv3 无激活时的最终 requantization 策略。

8.5 三层 DATAFLOW

三层融合后，Conv1、Conv2 和 Conv3 通过有限深度 FIFO 同时工作。整体吞吐由最慢 stage 决定，因此单独把某一层做到极高并行度不一定有收益。需要用实际 II 反向分配 DSP，使三层生产/消费速率尽量平衡。

FIFO 太浅可能产生 backpressure 或 deadlock，太深则浪费 BRAM。最终深度必须通过 co-simulation 和板上长时间重复运行验证。

10. PL/PS 集成与 Bring-up 顺序

为了避免把算法错误、HLS 接口错误和 DMA 错误混在一起，板级 bring-up 按由简到繁的顺序进行：

  1. 用 out[i] = in[i] + 1 dummy kernel 验证 HLS export；
  2. 在 Vivado 中连接 AXI DMA、HLS IP、clock/reset 和 PS；
  3. 生成 .bit/.hwh，完成 timing closure 和 DRC；
  4. 在 PYNQ 上验证 dummy 数据逐元素一致；
  5. 重复加载 overlay 和连续传输，检查是否 hang；
  6. 替换为单层 SRCNN，逐层对比 Golden dump；
  7. 接入完整三层 baseline；
  8. 最后启用 DATAFLOW 和高并行版本。

每一步都保存命令、工具版本、日志、report 和输入 checksum。只有 dummy DMA 链路稳定后，SRCNN 的错误才主要属于数值或算法路径。

11. 分层验证策略

同一套测试向量应依次通过以下验证链：

每层至少报告：

  • max_abs_error、MAE、RMSE 和 relative-L2；
  • 最大误差所在的 (channel, row, column)；
  • p50/p95/p99 absolute error；
  • ReLU zero flip 数量；
  • 输入、权重、bias 和各层 narrowing saturation 数量；
  • 最终图像相对 float Golden 的 PSNR/SSIM；
  • 如果有 HR ground truth，另外报告算法输出相对 HR 的 PSNR/SSIM。

“FPGA 是否忠实复现 Golden”和“SRCNN 对真实高分辨率图像的质量”是两个不同问题，不能使用同一个 PSNR 混在一起报告。

12. 性能与资源测量方法

12.1 三种时间边界

后续所有 FPS 和 speedup 都需要注明测量边界：

  1. Kernel-only：IP 从 start 到 done；
  2. Accelerator transaction：包含 DMA input/output；
  3. End-to-end：包含预处理、量化、DMA、kernel、反量化和后处理。

CPU baseline 必须使用同样的输入、权重、数据类型语义和线程设置。否则 speedup 没有可比性。

14. 下一步计划

  • 恢复正式训练权重、输入图像和参考输出，完成 P2.2b 定点格式选择；
  • 确认 KV260 exact part、Vitis/Vivado 版本和目标时钟；
  • 对无 pragma 的 srcnn_hls_top 运行第一次 csynth；
  • 用 dummy kernel 打通 HLS IP → Vivado BD → PYNQ DMA；
  • 固定 AXI packing、TLAST、传输长度和控制协议；
  • 为 Conv1/Conv3 实现 line buffer 和 sliding window；
  • 按实际 DSP/BRAM 预算选择三层 unroll factor；
  • 使用 DATAFLOW 串联三层，并通过 co-simulation 检查 deadlock；
  • 在 KV260 上完成逐层/端到端正确性测试；
  • 保存 kernel-only、DMA、端到端、资源、功耗与消融结果。

15. 阶段性总结

这个项目目前最有价值的部分，是先建立了一条可信的验证链，再进入硬件优化。SRCNN 的网络结构很短，但 5.22 亿 MAC、约 23.81 MiB 的中间 feature map、三层不平衡的计算密度和 PS/PL 数据移动，使它成为一个完整的 FPGA 系统问题，而不只是一个 HLS 循环展开练习。

后续优化的核心判断标准始终有三个：

  1. 数值结果是否仍然通过冻结的 Golden 与图像质量门限；
  2. 数据是否尽可能在 PL 内复用和流动，而不是频繁往返 DDR；
  3. 吞吐、资源与端到端时间是否都有可重复的实测证据。
