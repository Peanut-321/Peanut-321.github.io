“一张图进入 SRCNN 后，三层卷积分别在算什么，需要多少计算？”

软件侧先通过 Bicubic（双三次插值），根据原图已有的像素估计新增位置的像素值，将低分辨率图像放大到目标尺寸。PL 端接收形状为 1×255×255 的单通道图像，再利用 SRCNN 的三层卷积重建图像细节。

网络输入和输出的空间尺寸均为 255×255，三层的作用与输出形状如下：

层 作用 输出形状 激活
Conv1：9×9，1→64 提取局部特征 64×255×255 ReLU
Conv2：1×1，64→32 混合、映射特征通道 32×255×255 ReLU
Conv3：5×5，32→1 重建最终图像 1×255×255 无

Conv2 的 1×1 卷积只读取当前空间位置的特征，不直接访问相邻像素。不过，这些特征已经由 Conv1 的 9×9 卷积提取，因此仍包含邻域信息。

本项目采用 replicate-edge padding 处理边界：越界坐标被限制到最近的有效边缘像素，而不是补零。Conv1 和 Conv3 的 padding 半径分别为 4 和 2，使三层卷积都保持相同的空间尺寸。

当前卷积采用 cross-correlation（互相关）形式，计算时不翻转 kernel，而是将输入窗口与对应位置的权重逐项相乘并累加。

数据布局采用以下约定：

  • 激活张量：CHW，即 [channel][row][column]。
  • 权重张量：OIHW，即 [output-channel][input-channel][kernel-row][kernel-column]。

CHW 将每个通道的像素按行连续存储，便于逐行读取并使用 line buffer 缓存历史行。OIHW 则将同一输出通道对应的各输入通道权重连续存储，便于按输出通道组织计算。

  • Conv1：337,089,600 MAC，约 64.5%
  • Conv2：133,171,200 MAC，约 25.5%

2.1 功能契约与数据布局

Golden Reference 使用 float32 计算 SRCNN，为 HLS 仿真和 FPGA 输出提供比较基准。课程提交版遵循第一章的网络结构、replicate-edge 边界规则及 CHW/OIHW 布局；三层 stride 均为 1，每个输出通道对应一个 bias。

逐层比较沿用第一章的张量索引，并以 bias[output-channel] 对应各输出通道的偏置。

每个输出元素采用 bias-first 累加顺序：先用对应输出通道的 bias 初始化累加器，再按照输入通道、kernel 行、kernel 列的顺序逐项乘加。Conv1 和 Conv2 在完成全部累加后执行 ReLU；Conv3 直接输出累加结果，不执行额外激活。

2.2 手算与独立 Oracle 验证

Golden 自身也可能存在计算错误，因此需要通过结果可预测的手算用例和独立实现进行交叉检查。

全一测试

对每层分别注入全一输入，将权重全部设为 1、bias 设为 0。此时，每个输出元素等于参与累加的乘积数量：

单层测试 每个输出元素的预期值
Conv1 1×9×9 = 81
Conv2 64×1×1 = 64
Conv3 32×5×5 = 800

采用 replicate-edge padding 时，边缘位置重复读取的仍是数值为 1 的像素，因此边缘与中心的结果相同。这个测试用于检查累加项数与边界处理。上述预期值针对独立的单层测试；三层连续运行时，后一层接收前一层的输出，不能直接套用这些数值。

Bias-only 测试

对每层分别注入全零输入，并设置非零 bias。由于所有乘积均为零，输出只由 bias 和激活函数决定：Conv1 和 Conv2 应输出 max(0, bias[o])，Conv3 应直接输出 bias[o]，包括负值。测试同时使用正、负 bias，以检查偏置是否正确应用于各输出通道，以及 ReLU 是否只作用于 Conv1 和 Conv2。

独立 Oracle 验证

手算用例只能覆盖部分情况，因此还需要独立的 Python Oracle 交叉检查 C++ Golden。两者读取相同的输入、权重和 bias，但 Python 独立实现卷积索引、边界处理、累加与激活逻辑，不调用 C++ 的计算函数，以减少共享同一实现错误的可能。

这里需要区分验证范围：仓库现有 Python Oracle 覆盖内部 zero-same/valid 回归向量，其通过结论不能直接用于课程提交版的 replicate-edge 路径，后者需要对应的手算用例与参考输出验证。

除上述用例外，还需要检查以下行为；是否已经覆盖，应以实际测试代码和运行记录为准：

测试 主要检查目标
中心、边缘和角落 Padding 与空间索引
单个非零输入、非对称权重 Kernel 方向与输出位置
指定输入/输出通道的稀疏权重 通道映射与 OIHW 索引
正负输入、权重和 bias 有符号计算与 ReLU
非法形状、错误元素数量或损坏文件 输入检查与错误提示

2.4 可复现性

为区分代码改动与测试条件变化带来的影响，每次测试应固定输入、参数和运行配置，并保存以下信息：

项目 怎么做 为什么
输入 保存测试 tensor，记录 shape、数据类型和预处理方式 确保每次计算的是同一组像素值
权重与 bias 保存相同版本的参数文件 参数改变，输出就会改变
随机种子 生成随机向量时指定 seed 便于重新生成测试数据
Checksum 为文件或 tensor 计算校验值 检查数据是否被改动或损坏
工具版本 记录代码 commit、编译器版本和编译选项 工具与选项可能影响浮点结果

固定随机种子时，还应记录生成程序和随机数算法，并保存生成后的数据。校验值用于确认数据内容未变，不代表数据本身正确；复现测试时还需使用相同的运行命令和比较容差。

  • 舍入、溢出、饱和及层间重新量化发生在哪里？如何统计饱和事件？
  • 定点结果相对 float Golden 的误差如何传播？如何区分实现误差与图像质量？
  • 不同位宽在精度、DSP、存储和时序之间有什么取舍？最终选择依据是什么？

“怎样用有限位宽表示和计算这些数，既节省硬件，又不损失过多精度？”

3.1 动态范围与位宽分配

定点化的核心问题是：如何用有限位宽覆盖数值范围，同时保留足够的小数精度？

对于 ap_fixed<W, I>，W 为总位宽，I 为包含符号位的整数位宽，小数位宽为 W−I。总位宽固定时，增加整数位可以扩大表示范围，但会减少小数位，使量化间隔增大。

因此，位宽设计首先需要分析动态范围：使用正式权重和代表性输入，记录输入、各层权重与 bias、Conv1/2 激活前的累加值、激活后输出，以及 Conv3 输出的最小值和最大值。观测范围用于了解实际数据分布，还需要结合保守范围推导检查溢出风险。

乘法的完整结果通常需要更宽的表示，因此先保留乘积精度并使用较宽的 accumulator，完成累加和激活后再转换为层输出类型，避免每次乘加都提前缩窄。

累加器还需要为多项相加保留足够的整数位。Conv3 每个输出元素包含 800 项乘加，尤其需要关注累加过程中的范围；具体位宽仍取决于输入、权重和 bias 的大小，不能仅由累加项数决定。

3.2 舍入、饱和与层间量化

将宽结果转换为较窄类型时，需要分别处理小数精度和整数范围。AP_RND_CONV 采用最近舍入，恰好位于中点时选择偶数编码，以减少固定方向的舍入偏差；AP_SAT 则将越界结果限制在目标类型的最大值或最小值，避免回绕。

例如，ap_fixed<16, 4, AP_RND_CONV, AP_SAT> 显式指定了总位宽、整数位宽、舍入方式和饱和方式。饱和事件需要单独统计：转换前的宽值超过目标最大值时记录上溢饱和，低于目标最小值时记录下溢饱和。

层间量化发生在累加结果转换为层输出类型时。例如，accumulator 有 20 位小数，而下一层输入只有 10 位小数，那么保存当前层输出时就需要舍入到新的精度：

对应 3.1 的数据通路，Conv1/2 在 ReLU 之后转换为层输出类型；Conv3 不执行 ReLU，直接将宽位累加结果转换为最终输出类型。

3.3 精度与硬件成本的取舍

位宽会同时影响数值精度、运算资源、存储和时序，需要结合精度实验与硬件实现进行比较：

维度 位宽较小时 位宽较大时
精度 可用小数位较少，量化误差可能增大；整数位不足还会溢出 能保留更多精度或覆盖更大范围
DSP 乘法器可能更省资源，具体取决于 DSP 端口及综合映射 宽乘法可能需要多个 DSP
存储 权重、特征图和 FIFO 占用更小 BRAM/URAM 和数据传输需求更大
时序 较窄的运算通常更容易满足时钟要求 加法、乘法及布线可能更复杂，需要更多流水级

实际 DSP、BRAM 和时序收益取决于器件结构与综合映射，需要以报告为准，不能仅按位宽比例推算。

3.4 本项目的 Q20.12 选择依据

本项目保持 32-bit 数据字，将部分整数位分配给小数位，以提高精度。以下结果来自正式提供的 14 张图像，包括一张 Set5 图像和十三张 Set14 图像，并非完整基准集。

工程筛选条件为：每张图相对 float 的重建 PSNR 绝对变化不超过 0.1 dB，定点输出与 float 输出的一致性 PSNR 至少为 50 dB，同时通过饱和检查和正式模型的范围验证。

格式 小数精度 相对 float 的最大单图重建 PSNR 变化 最低定点/浮点一致性 PSNR 筛选结果
Q24.8 1/256 9.631357 dB 25.621040 dB 不通过
Q22.10 1/1024 0.140636 dB 50.212929 dB 不通过
Q20.12 1/4096 0.004187 dB 60.621163 dB 通过
Q18.14 1/16384 0.001065 dB 77.116276 dB 通过

这里的“重建 PSNR 变化”比较两种实现各自相对高分辨率真值的图像质量；“定点/浮点一致性 PSNR”则直接比较定点与 float 输出，衡量实现误差。

Q24.8 将 Conv1 中 1,205 个原本非零的权重量化为零，而 Q20.12 降至 117 个，Conv1 权重总数为 5,184。增加小数位保留了更多小权重信息。Q20.12 的三层累加器分别采用 31、37、44 bit，均保留 24 位小数。

Q18.14 的数值一致性更高，但 Q20.12 已满足工程精度门限，是已测试配置中小数位最少的通过者，因此被选入后续硬件验证。Q18.14 尚未完成同等硬件评估，不能据此认定 Q20.12 是所有候选格式中的最优方案。

精度通过后，还需要检查调度与实现结果。首次切换至 Q20.12 时，Conv1 MAC 循环的 II 从 1 增至 2；修复累加写回结构后恢复为 II=1。具体修改、资源代价与 RTL 对照结果见 4.3 的案例二。

前期 Q24.8/Q20.12 对比实现的布线后资源如下，区别于第八章记录的最终 V3 集成版本：

资源 Q24.8 Q20.12
DSP 86 86
LUT 15,739 15,986
FF 16,456 17,546
BRAM tile 等效数量 97 97.5

该次 Q20.12 实现在 5 ns、约 200 MHz 下通过布线时序，setup WNS 为 +0.107 ns。两种格式的数据字均为 32 bit，因此存储和传输宽度没有减小，资源占用也基本相近。两次独立实现运行存在布局布线差异，小幅资源变化不能全部归因于数值格式。

Q20.12 最终通过范围检查、RTL 与板级一致性验证：这次格式调整提高了精度，同时保持相近的硬件成本与原有 Conv1 MAC 吞吐。

“怎样组织计算、缓存和流水线，把三层卷积变成高效的 FPGA 电路？”

第一章计算的两层中间特征图合计约 23.81 MiB。若每帧都写回 DDR 再读入，会额外传输约 47.63 MiB；整帧保留在片上也超出本设计的存储预算。因此，本项目采用行缓存与层间 FIFO，只保留窗口计算需要的历史数据，并让下一层直接消费上一层结果。

Conv3：5×5 重建层

  • 32 个通道的空间窗口如何组织？800 项归约如何分组和流水化？
  • 如何处理部分和、累加精度与最终输出转换？

Conv3 先保存多通道邻域，再复用计算资源完成重建。Conv2 在每个位置输出 32 个特征，而 Conv3 需要这 32 个通道各自的 5×5 邻域，共 800 个数。当前行、历史行与窗口的具体数组尺寸统一列在 4.2。

例如，计算输出 (10,10)，需要每个通道第 8～12 行、第 8～12 列的数据。当前行提供第 12 行，历史行缓存提供前四行；窗口保留最近五列，组成完整的 5×5 区域。32 个通道的窗口值分别乘以对应权重，累加 800 项，再转换为最终输出类型，不执行 ReLU。

先接收完整一行，再更新历史行和窗口，因此输入到达后不会立刻产生输出。它保留了必要的行缓存，但省去了完整中间特征图的存储与 DDR 往返。

4.2 Line Buffer 与 Sliding Window

  • 历史行、窗口寄存器与 halo 分别需要多少存储？边缘像素如何复制？
  • 存储如何 banking/partition？读写端口是否满足并行需求？
  • 每帧启动、窗口填充、尾部排空与反压时如何保持坐标和数据一致？

输入按行到达，而卷积需要同时访问多行、多列的数据，因此使用当前行、历史行和窗口三类存储。以 Conv1 为例：

  1. 当前行缓存 row[255]：先接收一整行的 255 个像素，再交给窗口生成逻辑处理。
  2. 历史行缓存 line_buffer[8][263]：保留前八行，与当前行一起提供九行数据。列宽包含左右各四列 padding，因此为 255+8=263。
  3. 当前窗口 window[9][9]：保存本次卷积需要的 81 个值。向右移动一格时，丢弃最左一列，保留其余 72 个值，再从当前行和历史行补入右侧新的一列，共 9 个值。

Conv3 采用相同方式，但需要保存 32 个通道的 5×5 邻域。两层的数组尺寸如下：

存储 Conv1 Conv3
当前行缓存 [255] [32][255]
历史行缓存 [8][263] [4][32][259]
当前窗口 [9][9] [32][5][5]

边界采用 replicate-edge：上下重复首末行，左右重复首末列，补出的边界区域称为 halo。Conv3 左右各扩展两列，因此历史行缓存的列宽为 255+4=259。这些边界值在处理过程中生成，无需在 DDR 中另外保存完整的扩展图像。

启动与窗口有效性

每帧先清零历史行和窗口，并重新初始化扩展行计数。Conv1 收集满 9 行、9 列扩展数据后，才计算第一个有效位置；Conv3 则需要 5 行、5 列。换行时不清空窗口，而是在行首先移入新列，待上一行残留的列全部被替换后再恢复计算。初始化清零用于清理旧数据，实际边界仍由边缘复制生成。

帧尾与反压

最后一行输入结束后，Conv1 额外重复末行 4 次，Conv3 重复 2 次，完成底部边界计算。随后还需将流水线和 FIFO 中的结果全部传出，因此输入接收结束不等于整帧处理结束。

FIFO 满时，write() 等待空位；FIFO 空时，read() 等待新数据。其他阶段仍可处理已有数据，直到各自遇到阻塞，因此反压逐级传播，而非整条流水线立即同时暂停。

整帧输出以最后一个像素成功传输为结束标志；对应的 AXI-Stream 握手、反压信号保持与 TLAST 约定见 5.2。

当 TVALID=1、TREADY=0 时，发送方必须保持 TVALID，并保持 TDATA、TKEEP、TSTRB 和 TLAST 不变，直到握手完成。因此，即使最后一拍已经设置 TLAST=1，只要接收方尚未就绪，这一拍就仍未传输完成。

5.3 数据路径与 DMA 配置

图像经 DMA 传输，模型由 SRCNN 自行读取，完整路径见第四章。DMA 采用 Simple 模式，每次按 5.1 的顺序配置输入、输出 buffer 的物理地址和传输字节数，再由硬件完成整帧搬运，无须 CPU 逐个传送像素。模型参数不计入图像 DMA 的传输长度。

5.4 反压、错误恢复与带宽测量

等待过程中检查 DMA 错误位并设置超时，避免无限阻塞。发生错误或超时时，不能只复位 DMA 后立即释放 buffer：SRCNN 的 AXI master 可能仍在读取模型。runner 会尝试重新加载 overlay，确认硬件停止活动后再释放内存；恢复失败则保留 buffer，要求进一步复位或重新上电。

6.2 Overlay 加载与数据 Buffer 管理

1. Overlay：加载硬件并获取控制接口

加载 overlay，使 FPGA 具备 SRCNN 加速器及其配套电路。它对应一对匹配的文件：

  • .bit：配置 FPGA，在 PL 中形成 DMA、SRCNN 等硬件。
  • .hwh：描述硬件的接口、地址等信息，供 PYNQ 解析。

2. 连续内存 buffer：提供硬件可访问的内存

通过 PYNQ 的 allocate() 分配物理连续的 DDR 内存，并通过 physical_address 获取其物理地址。输入、输出和模型分别使用独立的 buffer，存放待计算图像、FPGA 写回的结果，以及权重与 bias；确认硬件完成访问后再释放。

3. dtype、shape 与打包：保持软硬件的数据约定一致

  • dtype：约定每个元素的存储类型、字节数及内容含义。
  • shape：图像的逻辑维度为 [1][255][255]，传输时按约定顺序展开为一维的 65,025 个元素，而不是改变图像本身的内容。
  • 打包：约定元素在内存中如何排列、如何传输，使 PS 和 PL 对同一段数据的解释一致。

1. HLS IP 如何接入 Vivado？

将 HLS 模块导出为 IP，在 Block Design 中连接 PS、DMA、SRCNN 和 AXI 互联，再配置时钟、复位和地址。

最终结构使用 HPM1 访问控制寄存器，通过 HPC0 访问 DDR，PL 工作频率约为 200 MHz。

2. Dummy Kernel

先用简单计算验证传输链路，再替换成完整网络，将“系统连接问题”和“卷积计算问题”分开排查。

  • Implementation：布局布线后，设计能否满足时序要求？
  • DRC：有没有违反硬件设计规则？
  • Timing report：哪些路径限制了时钟频率？
  • ILA（Integrated Logic Analyzer）：用于观察 PL 内部信号，包括 Stream 的 TVALID、TREADY、TLAST，以及复位和数据变化。

案例三：aux_reset_in 复位配置修正

系统集成时，辅助复位输入 aux_reset_in 已配置为低电平有效，却将这个未使用的输入接到了常量 0，导致 AXI 互联、DMA 和 SRCNN 一直处于复位状态，无法正常工作。修复时将该输入改接常量 1，重新生成硬件，并通过仿真确认复位能够正常释放。
